# Guita architecture

Technical reference for developers. For a quick overview and how to build and
run the project, see the [README](../README.md).

## 1. Goals

A single C++ code base that produces:

| Mode | Client | Backend | Database |
|---|---|---|---|
| **Web** | Qt/QML compiled to WebAssembly | remote server, over the persistent channel | server PostgreSQL |
| **Desktop connected** | native Qt/QML | remote server, over the persistent channel | server PostgreSQL |
| **Desktop standalone** | native Qt/QML | backend embedded in the client process, called in process | local PostgreSQL (embedded instance planned, see §11) |

Principles:

- The **client always talks to the backend through the RPC contract** and never
  knows which transport carries the calls and the server's events: a
  persistent WebSocket channel in the web and connected modes, in process in
  standalone mode. No shortcut skips the contract.
- **All business logic lives in the backend** (plain C++: cpp-httplib, libpqxx,
  protobuf). The client only presents data and validates for user experience; the
  backend repeats every critical validation, because the WASM client is in the
  user's hands.
- **Same engine (PostgreSQL), same SQL and same migrations** in every mode.
- The **backend never depends on Qt** and the **client never accesses the database**.
- The backend uses **small libraries, not a framework**: an embedded HTTP
  server, a PostgreSQL client and Protobuf, all with permissive licenses.

## 3. Source layout and build targets

```text
src/
├── proto/                   client-backend contract (Protobuf, buf module)
│   ├── guita/v1/            package guita.v1: the API
│   └── guita/channel/v1/    package guita.channel.v1: frames of the persistent channel
├── backend/                 backend, native only (never built for WASM)
│   ├── core/                domain, persistence (libpqxx), migrations, services
│   ├── api/                 RPC router, its transports and Backend
│   └── server/              server executable
└── client/                  Qt/QML client, native and WASM
    └── translations/        Qt Linguist catalogs
tests/                       automated tests (§10)
scripts/                     dependency setup, WASM build, server launcher, DB SQL
docs/                        this document
```

| CMake target | Type | Contents | Links |
|---|---|---|---|
| `contract` | static | code generated by `protoc` from `src/proto` (`guita::v1`, `guita::channel::v1`), native and WASM, lite runtime | `protobuf::libprotobuf-lite` |
| `core` | static | `backend/core` | `libpqxx::pqxx` |
| `api` | static | `backend/api` | `core`, `contract`; privately `httplib::httplib` |
| `server` | executable | `backend/server` | `api` |
| `client` | executable + `Guita` QML module | `client` | Qt Quick, Qt WebSockets, `contract`; `api` on native builds |

Dependencies flow `client → api → core`, and the client reaches the backend
only through `backend/api/Backend.h`, solely for standalone mode. The root
`CMakeLists.txt` adds `src/backend` only when not building for Emscripten.

The contract in `src/proto` is the single definition of the API, and it is
generated once, by `protoc`, for both sides: `contract` (`guita::v1`, no Qt)
is linked by the backend and by the client, natively and in WebAssembly, so
both run exactly the same code of the contract. Generated headers are
included as `<guita/v1/invoice_service.pb.h>` and
`<guita/channel/v1/channel.pb.h>`.

The contract has two packages. `guita.v1` is the API: messages and services.
`guita.channel.v1` holds the frames of the persistent channel (§4.3), the
framing of a transport rather than part of the API: a frame names the
procedure it carries in full (`guita.v1.InvoiceService/CreateInvoice`), so a
later `guita.v2` would travel over the same channel. The client first used Qt
Protobuf, a second generator with Qt types; it was dropped because QML cannot
read its `int64` fields anyway (the repositories adapt the messages), and
because protoc's code is far faster, also in WebAssembly (§4.5).

The contract is generated for protobuf's lite runtime (`option optimize_for =
LITE_RUNTIME`), on both sides, linked with `libprotobuf-lite`: the same speed
as the full library and a small fraction of its size in `client.wasm`. Lite
messages have no descriptors, reflection, text format or JSON, which the
project does not need: the API is binary (§4.3), the router checks the
contract by type names, and the command-line tools (`buf curl`, `protoc
--encode`/`--decode`) read and write messages by hand from the `.proto`.
Unknown fields are kept as bytes, so a message of a later version survives a
read and a write unchanged.

The contract evolves under rules that keep deployed clients and servers of
other versions working in binary, and keep the field names stable for the
tools that write messages by hand in JSON or text format:

- never reuse, renumber, retype or rename a field; removed fields reserve
  their number and name (`reserved`); add instead of changing meanings;
- one request and one response message per method;
- before a version is released anything may change; after it, incompatible
  changes go to a new package (`guita.v2`), served next to the old one.

`buf lint` (`STANDARD` rules) and `buf format` run as CTest tests.
`scripts/check-contract.sh [<git ref>]` runs `buf breaking` with the
`WIRE_JSON` rules against the development branch (by default
`origin/develop/vX.Y.Z`, from the CMake version); when that branch has no
contract yet there is nothing to compare. The CI runs it on every push and
pull request (§10.4). `WIRE_JSON` rather than `WIRE` because the names matter to those
tools and to any later JSON mapping. The stricter `FILE` rules are not used:
they protect the generated source code and forbid even reserved removals.
Project headers are included with angle brackets from `src/`
(`<backend/core/InvoiceService.h>`, `<client/ApiConnection.h>`). The whole
project is C++26, built by GCC 16 natively and by Emscripten's Clang for the
web client (§8). Executables are written to `build/<preset>/bin`.

## 4. Backend

### 4.1 Persistence (`backend/core`)

There is no ORM: SQL is explicit and lives in one place per aggregate.

- **Entities** are plain structs (`Invoice`, `NewInvoice`); nullable columns are
  `std::optional`.
- **Money** is never floating point: amounts are integer cents (`Cents`,
  `std::int64_t`) in C++ and in the API (`total_cents`), and `numeric(12,2)` in
  PostgreSQL. The store converts in SQL (`$3::numeric / 100` on write,
  `(total * 100)::bigint` on read), and a `CHECK` constraint backs the
  service's validation.
- **Stores** (`InvoiceStore`) hold all the SQL of an aggregate. A store works
  inside the caller's transaction (`InvoiceStore(tx).insert(...)`) and maps rows
  to structs with `pqxx` tuple conversions.
- **Prepared statements**: every store registers its statements in a static
  `prepare(pqxx::connection &)`, and `prepareStatements()` (`Statements.cpp`)
  calls them all on each new connection. The backend opens one connection at
  startup (`Database::warmUp()`), so a statement that does not match the schema
  fails at startup, not when a user reaches that screen.
- **Connection pool**: `pqxx::connection` is not thread-safe and the HTTP
  server handles requests concurrently. `Database` lends a pooled connection
  for each transaction; broken connections are dropped and reopened on demand.
- **Transactions**: services decide their boundaries with
  `db.inTransaction([&](pqxx::work &tx) { ... })`, which commits when the
  lambda returns and rolls back when it throws.
- **Optimistic locking**: every table has a `version` column. Updates use
  `UPDATE ... SET ..., version = version + 1 WHERE id = $1 AND version = $2`
  and treat zero affected rows as a concurrent modification.
- **Idempotency**: operations that create or modify take a request ID, a UUID
  chosen by the caller, kept with the data in the same transaction. Invoices
  keep it in a unique `request_id` column: the store inserts with `ON
  CONFLICT (request_id) DO NOTHING` and, when nothing was inserted, reads the
  invoice of that key. A concurrent insert of the same key waits for the
  first transaction to commit, so exactly one invoice is created. The service
  returns that invoice when the request matches it and rejects the key
  otherwise.
- **Services** (`InvoiceService`) hold the business rules, use stores and
  throw `std::invalid_argument` for validation errors.

### 4.2 Migrations

The schema is managed by numbered SQL migrations in `Migrations.cpp`, applied
at startup by the server and by standalone mode alike, before the statements
are prepared:

- `schema_version` records the applied versions.
- Everything runs in one transaction (PostgreSQL has transactional DDL),
  serialized between instances with `pg_advisory_xact_lock`.
- One statement per migration; a released migration is never edited, a new one
  is added. Until a version is released the migrations may still change, and
  development databases are created again. Table and column names are English `snake_case`; every table has a
  `bigserial` `id` and an integer `version`.

### 4.3 RPC API (`backend/api`)

The API is the contract of `src/proto` (§3), served as unary RPC procedures.
Dispatch does not depend on the transport:

- **`RpcRouter`** knows procedures, not transports. It takes an `RpcCall`
  (procedure, binary request, authorization) and returns an `RpcResult`
  (Connect code, binary response or error message). It checks the
  authorization, finds the procedure, decodes the request (skipping fields the
  contract does not define, of a later version) and encodes the response, and
  turns exceptions into codes: `std::invalid_argument` into
  `invalid_argument` with its message, anything else into `internal`
  (logged). Handlers are registered typed
  (`add<Request, Response>("guita.v1.InvoiceService/CreateInvoice", ...)`).
  The messages carry no descriptors, so registration checks the names of
  their types against the method, `guita.v1.CreateInvoiceRequest` and
  `guita.v1.CreateInvoiceResponse` (the convention `buf lint` enforces), and
  fails at startup with types of another method or package. Once registered,
  `call()` and `subscribe()` are thread-safe.
- **Stream procedures** carry server events. They are registered with
  `addStream<Request, Response>()`, whose handler gets the request and a
  function that sends one response message, and returns the handle of its
  subscription. `subscribe(RpcCall, onMessage)` checks the authorization and
  decodes the request like `call()`, and returns an `RpcSubscription`: an
  error, or a move-only handle that delivers the encoded messages to
  `onMessage`, in the thread that produces them, until it is released.
  `call()` of a stream procedure, or `subscribe()` to a unary one, answers
  `unimplemented`.
- **Events** are published on an `EventTopic<Message>`: every subscriber gets
  each message in the publisher's thread, in order, and is never called
  again once its handle is released. Subscribers must not block: they only
  queue the message for their transport. `InvoiceService` knows nothing of the
  contract: it takes a plain notification, called with each new invoice once
  its transaction is committed (never for a repeated request nor a failed
  one), which `publishCreatedInvoices()` turns into a `created` event.
  `WatchInvoices` subscribes to that topic and sends `started` first, under
  the topic's lock, so no invoice can arrive before it. Events reach the
  subscribers of the same process whatever transport created the invoice;
  they are delivered at most once, and those produced while a subscriber is
  disconnected are lost: `started` tells it to reload what it shows.
- **`InvoiceProcedures`** registers `guita.v1.InvoiceService` and converts
  between the contract's messages and the domain structs of `core`, which
  knows nothing of the contract.
- **Transports** adapt their own framing to `RpcCall`: `HttpRpcTransport` and
  `WebSocketRpcTransport` (the persistent channel) for the server, and
  `Backend::call()` and `Backend::subscribe()` for in-process calls of the
  standalone client (§6).

| Procedure | Request | Response |
|---|---|---|
| `guita.v1.InvoiceService/ListInvoices` | `ListInvoicesRequest {}` | `ListInvoicesResponse { invoices }`, in creation order |
| `guita.v1.InvoiceService/CreateInvoice` | `CreateInvoiceRequest { customer, optional customer_tax_id, total_cents, request_id }` | `CreateInvoiceResponse { invoice }` |
| `guita.v1.InvoiceService/WatchInvoices` | `WatchInvoicesRequest {}` | stream of `WatchInvoicesResponse { oneof event { started, created } }` |

The sample domain is a minimal invoice: a required customer, an optional
customer tax ID (an empty one is stored as absent) and a total in cents, which
must be a whole number between 0 and 999 999 999 999.

`CreateInvoice` is idempotent with a `request_id` (§4.1), whatever the
transport: a request repeated with the same key, also at the same time,
returns the invoice created the first time and creates no other; the key with
different data, or a key that is not a UUID, is an `invalid_argument` error;
without a key every request creates an invoice. The client sets a new key for
every invoice it creates, so it can safely send the request again after a
lost connection (§5.1). Numbering, dates and
invoice lines are not modeled yet. Error messages are English and not
translated yet.

**Over HTTP** (`HttpRpcTransport`), the unary subset of the Connect protocol:

- `POST /api/<package>.<Service>/<Method>`, with the request and the response
  in binary Protobuf (`Content-Type: application/proto`); any other content
  type, `application/json` included, gets `415`.
- `Connect-Protocol-Version: 1` is accepted and not required, so Connect
  clients and tools that use the binary codec, such as `buf curl`, can call
  the API with `/api` as prefix. Connect clients that default to JSON (such as
  connect-web) need the binary codec configured.
- Errors are Connect errors, `{"code": "...", "message": "..."}` as JSON (as
  Connect defines them for any codec, written by `connectErrorBody()`), with
  these statuses: `invalid_argument` 400, `unauthenticated` 401,
  `unimplemented` 404 (unknown or stream procedure) or 415 (content type), `internal`
  500; other HTTP methods on a procedure get `405` with `Allow: POST`.
- Responses are compressed with gzip when the client accepts it (cpp-httplib is
  built with zlib); request bodies are limited to 16 MiB.

The API serves no JSON, but its messages can still be written and read by hand
with the contract. `buf curl` takes the request in JSON, sends it in binary and
prints the response in JSON; `protoc --encode` and `--decode` convert between
Protobuf's text format and binary, for example to send a hand-written request
with `curl` or to read a captured message:

```sh
buf curl --schema src/proto --data '{}' \
     http://127.0.0.1:8090/api/guita.v1.InvoiceService/ListInvoices

echo 'customer: "Acme S.L." total_cents: 121000' |
  protoc -I src/proto --encode=guita.v1.CreateInvoiceRequest guita/v1/invoice_service.proto |
  curl -s --data-binary @- -H 'Content-Type: application/proto' \
       http://127.0.0.1:8090/api/guita.v1.InvoiceService/CreateInvoice |
  protoc -I src/proto --decode=guita.v1.CreateInvoiceResponse guita/v1/invoice_service.proto
```

With `request_id: "9b2f0c1e-5d43-4a8e-b6f7-0e1d2c3b4a59"` added to that text,
running the command twice prints the same invoice both times.

**Over the persistent channel** (`WebSocketRpcTransport`), a WebSocket at
`/api/channel` on the same port, which carries calls and events over one
long-lived connection:

- One binary message is one frame of `guita.channel.v1` (§3): the client
  sends `ClientFrame`s (`hello`, `call`, `cancel`) and the server answers with
  `ServerFrame`s (`welcome`, `reply`, `message`, `goodbye`).
- The first frame must be a `hello` with the authorization, as in the HTTP
  header (`Bearer <token>`): browsers cannot set headers on a WebSocket
  handshake. The server checks it with the same `Authorizer` and answers
  `welcome`; a wrong token gets a `goodbye` with `unauthenticated`, and any
  other first frame a `goodbye` with `invalid_argument`, before the
  connection is closed (1008, 1002). A connection that sends no `hello` in 10
  seconds is closed.
- A `call` carries a correlation ID chosen by the client, unique among its
  calls in flight, the full name of the procedure and the encoded request.
  Unary calls run on a worker pool shared by all channels, several at once
  per channel, and their `reply` (the response, or an error with its Connect
  code and message, the same as over HTTP) carries the call's ID and goes
  out as soon as the call finishes, whatever the order of the calls. An ID
  already in flight is answered with `invalid_argument`. After 64 unary
  calls in flight the channel stops reading until one finishes, so TCP slows
  the client down.
- A `call` to a stream procedure opens a subscription: each of its messages
  goes out as a `message` with the call's ID, until a `cancel` with that ID
  or the end of the connection. An error opening it is a `reply`.
- Text messages, undecodable frames or a second `hello` close the
  connection (1003, 1002) after a `goodbye`. Frames over 16 MiB are refused,
  as HTTP bodies are.
- Each channel reads in a thread of the HTTP server and writes from a thread
  of its own, which sends the queue of outgoing frames: whoever produces a
  reply or an event only queues it. A client that does not read and leaves
  more than 1 MiB queued is closed (1008), without holding the producer nor
  the other channels.
- At most `WS_MAX_CHANNELS` channels are open at once (64 by default); one
  more is closed at once with 1013 (*Try Again Later*). The server's thread
  pool gets one more thread per channel, so HTTP, and with it the web
  client's files, always has threads of its own.
- cpp-httplib pings every channel every 30 seconds and closes it after two
  unanswered pings. `Backend::stop()` closes the open channels (1001) before
  stopping the server, so it does not wait for their clients.

### 4.4 Backend and server

`Backend` assembles database, services, the RPC router and, optionally, the
network transports (HTTP and the persistent channel), and is shared by the
`server` executable and standalone mode. It is configured with
`BackendOptions`: connection string, authorizer and optional `HttpOptions`
(address, port, docroot, access log, maximum of channels). Its constructor
applies the migrations, prepares the statements and registers the procedures,
and throws on failure. `call()` runs a procedure in the caller's thread;
`subscribe()` opens a subscription to a stream procedure, whose messages
arrive in the thread that produces them (the first one possibly before
`subscribe()` returns);
`start()` binds the port and runs the HTTP server on its own thread pool
without blocking (with port `0` the OS picks a free port, returned by
`port()`). Without `HttpOptions` nothing listens on the network.

`Backend.h` exposes only `RpcCall`, `RpcResult`, `RpcSubscription` and standard types, and
includes neither cpp-httplib, libpqxx nor protobuf (pimpl), so the client only
sees that small interface.

With a docroot, the same server serves the WASM files (`.wasm` as
`application/wasm`). The `server` executable blocks `SIGINT` and `SIGTERM`
before any thread starts and waits for them with `sigwait()` to stop cleanly.
It is configured through environment variables:

| Variable | Default | Purpose |
|---|---|---|
| `DB_CONN` | `host=127.0.0.1 dbname=guita user=guita password=guita` | libpq connection string |
| `HTTP_ADDRESS` | `0.0.0.0` | listen address |
| `HTTP_PORT` | `8090` | port |
| `DOCROOT` | `./web` | static files (WASM build) |
| `WS_MAX_CHANNELS` | `64` | persistent channels open at once |
| `API_TOKEN` | empty | required Bearer token; empty accepts everything (development only) |

### 4.5 Measurements

Two programs in `tests/bench`, outside `ctest`, built in Release with the
`bench` preset (native) and `wasm-bench` (WebAssembly):

```sh
cmake --preset bench && cmake --build --preset bench
build/bench/bin/bench_encoding
build/bench/bin/bench_latency            # --quick: a twentieth of the calls
```

**Round trip of a small call per transport** (`bench_latency`, loopback, a
stub procedure without database, so only the transport is measured). The
persistent channel is measured whole, with the envelope, the session, the
worker pool and the writer thread of `WebSocketRpcTransport`, both with
cpp-httplib's client and with the client's own `WebSocketTransport` in a Qt
event loop:

| Transport | p50 | p90 | p99 |
|---|---|---|---|
| `RpcRouter::call()` directly | 0.1 µs | 0.1 µs | 0.2 µs |
| In process: pool thread + event queue (as `InProcTransport`) | 9.4 µs | 10 µs | 14 µs |
| HTTP `POST`, keep-alive, empty body | 36 µs | 44 µs | 104 µs |
| HTTP `POST`, keep-alive, 8-byte body | 41 µs | 52 µs | 107 µs |
| WebSocket frame, same bytes as the empty body | 41 µs | 48 µs | 60 µs |
| Persistent channel, cpp-httplib client | 56 µs | 61 µs | 74 µs |
| Persistent channel, `WebSocketTransport` (Qt) | 53 µs | 60 µs | 71 µs |

**Size of `client.wasm`**: 27 725 237 bytes before the contract, 27 941 331
with Qt Protobuf (+211 KiB), 28 886 336 with protoc's code on the full
`libprotobuf` (0.9 MiB more, measured while making this change) and 27 938 849 on
`libprotobuf-lite`: 2.4 KiB less than with Qt Protobuf, 0.8 % over no
contract at all. With the persistent channel it is 28 060 716 bytes: Qt
WebSockets and `WebSocketTransport` instead of `QNetworkAccessManager` and the
former HTTP transport, and the channel's frames in the contract, add 119 KiB
(0.4 %).

Reading:

- Protobuf messages are about 2.4 times smaller than JSON, and 1.3 to 1.5 times
  smaller once compressed, since gzip already removes most of JSON's
  repetition.
- protoc's code encodes 80 to 150 times faster than building JSON and decodes
  8 to 18 times faster than `QJsonDocument`, and runs in WebAssembly at about
  the speed it has natively. Compared with the former Qt Protobuf client, it
  encodes 35 to 50 times faster and decodes 6 to 15 times faster; its
  lite runtime costs no more in `client.wasm` than Qt Protobuf did.
- The in-process transport costs about a quarter of HTTP on loopback, and
  opens no socket at all. A real call adds the database time (hundreds of
  microseconds), which dominates either way.
- With cpp-httplib's client, a request with a body costs about 5 µs more than
  one without, whatever its encoding: headers and body are written apart.
- With cpp-httplib, a WebSocket frame is not faster than an HTTP request with
  keep-alive for request/response. The persistent channel exists for server
  events and one long-lived connection, not for the latency of one call: it
  costs about 15 µs more than a bare frame, the two thread hops that let
  several calls run at once and keep producers from waiting for the socket
  (to the worker pool and to the writer thread). A real call adds the
  database time, hundreds of microseconds, either way.
- Small request/response exchanges need `TCP_NODELAY`: without it, Nagle's
  algorithm and delayed ACKs made each WebSocket round trip take about 82 ms.
  The backend enables it on its HTTP server, which covers the channel; the Qt
  client needs nothing more, as its round trip above shows.

## 5. Client

### 5.1 API connection and repositories

`ApiConnection` is a `QML_SINGLETON` holding the mode (`Web`, `Connected`,
`Standalone`), the URL of the channel in the web and connected modes, the
transport and whether the backend is `available` now. `main.cpp` calls
`ApiConnection::configure()` before loading the QML, and QML gets the
instance through the static `create()`; the class is not default-constructible
on purpose (Qt prefers a default constructor over `create()`).

- `ApiConnection::call<Response>(procedure, request, context, onResponse,
  onError, repeat)` encodes the request (any message of the contract), hands
  the bytes to the transport and decodes the response. `repeat`
  (`Repeat::Never` by default, or `Repeat::Safe`) says whether the call may be
  sent again when the connection is lost before its reply: only reads and
  operations with a `request_id` are marked safe, so nothing is applied twice
  by mistake.
- `ApiConnection::subscribe<Response>(procedure, request, context, onMessage,
  onError)` subscribes to a stream procedure (server events) until `context`
  is destroyed; a message this version cannot decode is skipped.

The transport is an `ApiTransport`, invisible to QML, with two asynchronous
operations, a call and a subscription (results and messages in the UI thread
and only while the caller is alive), and a notification of whether the
backend is reachable:

- `WebSocketTransport` (web and connected): the persistent channel (§4.3) with
  Qt WebSockets, in the UI thread and without blocking waits:
  - the connection opens with the first call or subscription and sends the
    `hello` with the Bearer token; calls made meanwhile wait for the
    `welcome`, and each call and subscription gets a growing correlation ID;
  - when the connection is lost the backend is unavailable, and the
    transport reconnects while calls or subscriptions remain, waiting 0.5
    seconds, then twice as long each time up to 30 seconds, ±20 % so that
    clients cut off together do not come back together; a `welcome` resets
    the wait;
  - after the `welcome`, calls not sent yet go out in the order they were
    made; calls in flight when the connection was lost are sent again only
    if they are `Repeat::Safe`, and the others fail with "Connection to the
    backend lost"; subscriptions are opened again, so their messages start
    over (with `started` for `WatchInvoices`);
  - a call without reply 30 seconds after it was made fails with "Backend
    unavailable" (a subscription has no such limit);
  - a `goodbye` with `unauthenticated` fails what is pending with the
    backend's message, and the transport does not reconnect until the next
    call or subscription;
  - destroying the context of a subscription sends its `cancel`.
- `InProcTransport` (native only): builds an `RpcCall` and runs
  `Backend::call()` on a thread of its own `QThreadPool`, since the router is
  synchronous and PostgreSQL may take a while; the result comes back to the UI
  thread through the event queue. Subscriptions use `Backend::subscribe()`:
  each message comes from the thread that produced the event, also through
  the event queue. Other threads carry only an id and the result or message:
  pending callbacks and their context objects are kept and checked in the UI
  thread. The destructor ends the subscriptions and waits for the calls in
  flight. The backend is always available.

Repositories (`InvoiceRepository`) are `QML_ELEMENT`s instantiated by the view
that uses them, with a typed `REQUIRED` `connection` property. They build the
contract's messages, expose `Q_INVOKABLE` operations with typed arguments
(`create(customer, customerTaxId, totalCents)`) and report results through
signals as typed value types: `InvoiceRow` (`QML_VALUE_TYPE`), with `QString`
for the contract's UTF-8 strings and doubles for ids and totals, because QML's
`int` has 32 bits; doubles are exact up to 2^53. `create()` gives every
invoice a new `request_id` (`QUuid`) and is safe to repeat, like `list()`.
`watch()` subscribes, once per repository, to `WatchInvoices`: `watching()`
with each `started`, and `invoiceCreated()` with each invoice.

**Everything is asynchronous** (signals and callbacks): WebAssembly forbids
blocking waits and nested `QEventLoop::exec()`.

### 5.2 Views

Views live in the `Guita` QML module. C++ types reach QML only by declarative
registration (`QML_ELEMENT`, `QML_SINGLETON`), never through context
properties, `qmlRegister*` calls or objects injected from `main.cpp`. Views use
typed properties so `qmllint` checks every access.

`Main.qml` calls `watch()` when it loads and reloads the list on `watching()`
(the first time, and after every reconnection, which may have missed events)
and on `invoiceCreated()`, so the list follows what any client creates. It
shows a notice while `ApiConnection.available` is false.

Presentation logic worth testing lives in JavaScript libraries of the module
(`.pragma library`), such as `Amount.js`, which parses typed amounts into cents
and formats cents per locale; views import them and Qt Quick Test covers them
without loading any view.

### 5.3 Platform-specific pieces

Only three pieces differ between native and WASM:

- `ApiConfig.h`: in WASM the channel is at the page's host +
  `/api/channel`, `wss://` behind `https://` (same origin, so no CORS);
  natively it is beside `API_URL`, the API's base URL (default
  `http://127.0.0.1:8090/api/`, so `ws://127.0.0.1:8090/api/channel`).
- `main.cpp` and `InProcTransport`: standalone support (`APP_STANDALONE_SUPPORT`,
  defined only on native builds) embeds the backend and calls it in process.
- `WebKeyboard.cpp` (WASM only, installed by `main.cpp`): accents typed with
  dead keys. On a Spanish keyboard "é" is the dead key ´ and then e: the
  browser sends a `keydown` "Dead", a `keydown` "e" and an `input` event with
  the composed "é". Qt 6.12 for WebAssembly maps dead keys by their physical
  position for US and Mac layouts only, so it loses the Spanish one, inserts
  the "e" and drops the `input` event that carries the "é" ("Pérez" comes out
  as "Perez"). A `keydown` listener in the capture phase of `window`, which
  runs before Qt's, acts only while a Qt text field has focus (Qt then
  receives text through a hidden `<input>`): it keeps the dead key and the
  character key after it from reaching Qt, without cancelling them, so the
  browser inserts the composed text and Qt's input context takes it from the
  `input` event. Keys without a character (Backspace, arrows, Ctrl shortcuts)
  and input method compositions, which Qt handles, pass through.

  `tests/web/dead-keys.mjs` checks it by hand, outside `ctest`: it types,
  through Chrome's DevTools protocol, the very events a Spanish keyboard sends
  for "Pérez á´´xn" (synthetic dead keys from `xdotool` are not reliable), and
  the focused field must show exactly that. Repeat it when Qt is upgraded, to
  know whether the workaround is still needed:

  ```sh
  google-chrome --remote-debugging-port=9222 http://127.0.0.1:8090/
  # click a text field of the client, then
  node tests/web/dead-keys.mjs             # Node.js 22 or later
  ```

### 5.4 Internationalization

English is the source language: `qsTr()` in QML, `tr()` or
`QCoreApplication::translate()` in C++. Languages are declared in
`qt_standard_project_setup` and the catalogs (`src/client/translations/guita_*.ts`)
are embedded under `:/i18n`; `main.cpp` loads the one matching the system
locale (the browser locale in WASM). Refresh the catalogs with the
`update_translations` target.

## 6. Standalone mode

`client --standalone [--db <conn>]`:

1. Creates `Backend` without `HttpOptions`: nothing listens on the network,
   so the in-process calls need no credentials (its authorizer accepts them).
2. Configures `ApiConnection` with `InProcTransport` over that backend.

Calls run on the transport's pool threads, so they never block the UI.
Server events reach the views in this mode too: the transport subscribes
through `Backend::subscribe()`, so `WatchInvoices` behaves as over the channel
for invoices created in this process. `Backend` is declared before the QML
engine in `main()`, so it is destroyed after the views, the connection and
the transport (which ends its subscriptions and waits for the calls in
flight) are gone. Compared with the former loopback HTTP, there is no
socket, TCP, HTTP parsing nor token in this mode (§4.5 measures the
difference).

## 7. Authentication

Authentication is pluggable rather than tied to an identity provider:

- **Backend**: an `Authorizer` (`backend/api/Authorizer.h`) receives the
  `Authorization` header of every HTTP request, and the authorization of the
  `hello` that opens every persistent channel, and decides whether to accept
  it.
  `tokenAuthorizer()` implements the current shared-token check; validating
  tokens from any identity provider (for example JWTs from an OIDC server) is
  just another `Authorizer`, with no changes elsewhere.
- **Client**: the transport sends the Bearer token it is configured with in
  the channel's `hello`; whatever obtains the token only has to hand it over.

| Mode | Current |
|---|---|
| Web | none: the server runs without `API_TOKEN` (development only) |
| Desktop connected | shared `API_TOKEN` |
| Desktop standalone | none needed: in-process calls only, nothing listens on the network |

The shared `API_TOKEN` is a development aid, not user authentication. User
authentication owned by the backend (users in PostgreSQL, Argon2 password
hashes, session tokens issued by the backend) is pending (§11): it keeps every
mode self-contained, without external services.

- Node.js 22 or later is needed only for the manual check of the web
  client's dead keys, `tests/web/dead-keys.mjs` (§5.3).
- **The native compiler** (server, desktop client, tests and measurements) is
  GCC 16.2.0 built from the GNU sources by `scripts/build-gcc.sh`, configured
  as the official `gcc:16.2.0-trixie` image the CI runs in (§10.4):
  `--disable-multilib`, full bootstrap, C and C++ only. The local compiler and
  the CI's are therefore the same release with the same defaults (upstream
  GCC enables neither PIE nor the stack protector by default, unlike
  distribution packages). The script also fixes the `as` and `ld` found in the
  PATH (`--with-as`, `--with-ld`), so that a later change of PATH does not give
  that GCC other binutils than the ones it was configured with. The `native`
  preset sets it as `CMAKE_CXX_COMPILER`, and configuring fails early, before
  looking for Qt, with any compiler that is not GCC 16 or later accepting
  `-std=c++26 -freflection`. Reflection is not enabled on any target yet.
  `scripts/build-deps.sh` builds the native libraries with that GCC, so
  `scripts/build-gcc.sh` runs first.
- **The run path to GCC 16's `libstdc++`.** It is newer than the system's
  (`GLIBCXX_3.4.29` on EL9), so the native executables carry a run path to its
  directory: the project's through `CMAKE_BUILD_RPATH`, and `protoc` through
  `-Wl,-rpath` in `scripts/build-deps.sh`. They start without
  `LD_LIBRARY_PATH`, and the Qt libraries they load share that `libstdc++`,
  which is backward compatible with the one Qt was built against. Linking it
  statically would leave two standard libraries in one process, the static one
  and the shared one Qt loads. The run path is absolute: development builds
  are not relocatable, which desktop packaging will have to address (§9.2).
- **What the client may use.** The web client is built by the Clang of emsdk
  5.0.5 (Clang 23, a development snapshot), also in C++26 (`-std=gnu++26`).
  The client code goes through both compilers, so it uses only what that Clang
  and its libc++ support; the backend, native only, may use all of GCC 16.
  Measured with one small program per feature:

  | C++26 | Clang of emsdk 5.0.5 (client) | GCC 16.2 (backend) |
  |---|---|---|
  | Pack indexing (`T...[0]`), `= delete("reason")`, the `_` placeholder, structured bindings as a condition and as a pack, `#embed`, variadic friends, placement new in `constexpr`, user `static_assert` messages | yes | yes |
  | Reflection (`^^`, annotations, function parameters), expansion statements (`template for`), contracts, exceptions in `constexpr` | no | yes (reflection with `-freflection`, contracts with `-fcontracts`) |
  | Library: `inplace_vector`, `views::concat`, `function_ref`, `copyable_function`, `optional` as a range, `text_encoding`, `std::simd`, `<debugging>` | no | yes |

  The emsdk version follows Qt (next point), so this changes only when Qt is
  upgraded. The CI does not build the web client yet, so a change to
  `src/client` builds the `wasm` preset locally as well.
- The scripts install the non-system dependencies (GCC, Qt, emsdk, libpqxx,
  cpp-httplib, protobuf, buf) without root privileges under `$SOFTWARE_DIR` (default
  `~/software`), which is where the CMake presets look for them; with other
  locations, pass `CMAKE_PREFIX_PATH` or use a `CMakeUserPresets.json`.
  `scripts/setup-qt.sh --desktop-only` installs only the desktop kit, without
  the WASM kit, emsdk or Python: enough for the server, the native client and
  the tests, as in the CI (§10.4).
- The Qt WASM kit requires the desktop kit of the **same version** as host
  (`QT_HOST_PATH`) and a specific Emscripten release
  (`QT_EMCC_RECOMMENDED_VERSION` in `QtPublicWasmToolchainHelpers.cmake`):
  upgrade Qt and emsdk together.
- protobuf and abseil are built with the project's C++ standard, so that
  abseil and the project agree on the `std` types abseil aliases. Its `protoc`
  generates the contract's code of both builds, native and WebAssembly.
- The same protobuf and abseil are built again for WebAssembly
  (`~/software/protobuf-36.2-wasm`) with the emsdk of `scripts/setup-qt.sh`,
  which must therefore run first; without emsdk, `scripts/build-deps.sh` skips
  that part with a warning. They use what Qt's `wasm_singlethread` kit uses: no
  threads and Emscripten's default exception handling. Both builds must have
  the same version, which the generated code checks. The `wasm` preset finds
  that installation through `CMAKE_PREFIX_PATH` and `CMAKE_FIND_ROOT_PATH`
  (Emscripten's toolchain only searches its sysroot) and generates the code
  with the native `protoc` (`GUITA_HOST_PROTOBUF_DIR`).
- Emscripten needs Python ≥ 3.10 (`EMSDK_PYTHON`, set by the `wasm` preset and
  `scripts/build-wasm.sh`; `emsdk_env.sh` clears it).
- Presets: `native` (Debug, `build/native`) and `wasm` (Release, `build/wasm`).
  `scripts/build-wasm.sh` also copies the web files to `build/web`, the docroot
  used by `scripts/run-server.sh`.

## 9. Deployment

### 9.1 Server

```
/opt/guita/
├─ server            executable
└─ web/              WASM build: client.html (also as index.html), client.js,
                     client.wasm, qtloader.js
```

The same server serves the static files, the API and the persistent
channel. There is a single server, without horizontal scaling: server events
are produced and delivered within its process (§4.3). A reverse proxy in front
terminates TLS (and can speak HTTP/2 to browsers), for example HAProxy:

```
defaults
    mode http
    timeout client 30s
    timeout server 30s
    # Open WebSockets: longer than the server's 30-second ping
    timeout tunnel 1h

frontend https
    bind :443 ssl crt /etc/haproxy/certs/guita.pem
    default_backend guita

backend guita
    server guita1 127.0.0.1:8090 check
```

HAProxy passes the WebSocket upgrade of `/api/channel` through in HTTP mode
(`wss://` outside, `ws://` to the server); once upgraded, `timeout tunnel`
applies, and the server's pings keep an idle channel open.

COOP/COEP headers (`Cross-Origin-Opener-Policy: same-origin`,
`Cross-Origin-Embedder-Policy: require-corp`) are needed only if the client is
built with the multithreaded WASM kit; the project uses `wasm_singlethread`.
Everything is same-origin, so no CORS is needed.

A `manifest.json` plus a service worker caching `client.html`, `client.js`,
`client.wasm` and `qtloader.js` would make the web client installable as a PWA
and speed up later launches (the API still needs a connection).

### 9.2 Desktop

Not packaged yet. The package will ship the executable with the Qt 6.12
libraries (RUNPATH `$ORIGIN/lib`) and the Qt plugins and QML modules it uses;
the backend libraries are linked statically or are header-only, and libpq
comes from the system or the package.

## 10. Testing

### 10.1 Framework and layout

All tests use Qt Test, and Qt Quick Test for QML logic, and are registered in
CTest; they are native only and run headless (`QT_QPA_PLATFORM=offscreen`).
The web client's handling of dead keys is checked by hand with
`tests/web/dead-keys.mjs` (§5.3).
The backend tests link Qt only in their own executables: `core`, `api` and
`server` stay Qt-free.

- `tests/CMakeLists.txt` defines `guita_add_test(<name> LABELS ... [LIBS ...]
  [SOURCES ...] [DATABASE])`, which builds `test_<name>.cpp` against the layer
  under test. Helpers live in `tests/support/` and are included as
  `<support/...>`.
- Every suite has a label saying what it needs: `unit` (nothing), `db`
  (PostgreSQL), `api` (in-process backend and HTTP client), `client` (client
  classes against an embedded backend), `qml` (Qt Quick Test).
- `ctest --preset native` runs everything; `-L <label>` and `-LE <label>`
  select subsets; `-j` runs suites in parallel.

### 10.2 Ephemeral PostgreSQL

The database suites run against a real PostgreSQL, the only safety net of
explicit SQL. There is no mature Testcontainers for C++, so the same idea is
expressed with CTest fixtures:

- `postgres_start` (`FIXTURES_SETUP`) runs `tests/postgres-fixture.sh start`:
  without `GUITA_TEST_DB` it starts an ephemeral `postgres:18.6` container
  (`GUITA_TEST_PG_IMAGE` overrides the image) on a random loopback port with a
  random password, waits until it accepts connections and writes the
  connection string to a file in the build directory (`GUITA_TEST_DB_FILE`).
  With `GUITA_TEST_DB` set it only writes that string.
- `postgres_stop` (`FIXTURES_CLEANUP`) removes the container, also when suites
  fail. Suites declared with `DATABASE` require the fixture, so the container
  starts once per run and only when a selected suite needs it.
- Without Docker or `GUITA_TEST_DB`, `postgres_start` fails with instructions
  and the database suites are reported as not run (failed), never skipped.

`TestDatabase` (`tests/support/`) gives each suite a database of its own,
`guita_test_<suite>_<random>`, created empty from `template0` and dropped with
`WITH (FORCE)` on destruction. Suites apply the migrations themselves, run in
parallel without interfering, and leave nothing behind. No test ever uses the
application's default connection string.

### 10.4 Continuous integration

`.github/workflows/ci.yml` runs on GitHub Actions on every push to
`develop/**` and `release/**`, on every pull request toward them, and by hand
(`workflow_dispatch`, to try a change branch before its pull request). A
single job, `Build and test`, on `ubuntu-24.04` but inside the official
`gcc:16.2.0-trixie` image (Debian trixie with GCC 16.2.0 built from the GNU
sources, the same release and configure options as `scripts/build-gcc.sh`
installs locally, §8):

1. checks out the whole history, which `scripts/check-contract.sh` needs;
2. runs `scripts/check-version.sh` against the branch pushed to or the base
   branch of the pull request (manual runs have no branch to compare with);
3. checks that the image's GCC is the `GCC_VERSION` of `scripts/build-gcc.sh`,
   and fails otherwise, so that the local compiler and the CI's cannot drift
   apart;
4. installs with `apt` (as root, without `sudo`) what the project takes from
   the system and the image lacks: CMake, Ninja, the Python `venv` module for
   aqtinstall, libpq, zlib and the libraries Qt needs to build and run
   headless;
5. links `~/software/gcc-16.2.0` to the image's `/usr/local`, where the
   presets and `scripts/build-deps.sh` look for the compiler; the link stays
   out of the cache;
6. restores `~/software` from the cache or, when the key changed, installs it
   with `scripts/setup-qt.sh --desktop-only` and `scripts/build-deps.sh`,
   drops the sources, and saves it at once, so that a run whose tests fail
   keeps it. The key is the hash of both scripts plus the image
   (`toolchain-gcc-16.2.0-trixie-<hash>`), whose system and compiler the
   libraries are built with: changing a version in them reinstalls
   everything, and a cold run (mostly protobuf with abseil) is covered by the
   job's timeout;
7. runs `cmake --preset native`, `cmake --build --preset native` and
   `ctest --preset native --parallel`;
8. runs `scripts/check-contract.sh` against `origin/develop/vX.Y.Z`, also
   when the build or the tests fail, so that a pull request shows both kinds
   of problem at once. It runs every time, since it takes a second; on a push
   to the development branch itself it compares the contract with itself.

PostgreSQL is a `postgres:18.6` service container with a health check, given
to the tests in `GUITA_TEST_DB` and reached by its name (`host=postgres`),
since the job runs in a container too, so the fixture starts nothing: the
suites are the same locally and in CI, and only the provider of the server
changes. Docker Hub does not rate-limit the pulls of public images from
GitHub's runners. A new run of the same branch or pull request cancels the one
in progress, and the workflow only reads the repository (`contents: read`).
The WebAssembly build (#12; its job needs this image too, since
`scripts/build-deps.sh` builds the host `protoc` with GCC 16) and the
measurements of `tests/bench` are not part of the CI.

**Requiring it.** A repository ruleset, `develop and release`, on
`develop/**` and `release/**` (Settings → Rules → Rulesets) requires the `Build and test` status check, with
the branch up to date before merging, so that no pull request is merged while
the CI is red. GitHub only offers checks it has already seen, so the ruleset is
created after the first run, and the job keeps its name.

    distribution. The LGPL then requires letting users relink the client with
    a modified Qt (for example by publishing the client's sources or object
    files); with this project's sources public under MIT, that is covered.
  - Avoid Qt modules available only under the GPL or commercially, which would
    impose the GPL on distributed builds.
- **Concurrency:** the HTTP server handles requests in parallel on a thread
  pool, one thread per connection. A persistent channel holds three threads
  while open: the server's thread that reads, cpp-httplib's ping thread and
  its writer. That suits business applications, with tens or hundreds of
  users on one server, but not tens of thousands of simultaneous connections;
  hence the limit of channels, and the pool sized so that HTTP keeps its own
  threads. An event-loop server would remove the limit (§11) and only touch
  `WebSocketRpcTransport`. Services stay thread-safe through the connection
  pool and one transaction per call.
- **Standalone security:** in-process calls only: no listening socket at all.
